\begin{abstract}
Scientific programs written in Fortran decades ago are still in daily use, but most of their routines have no documentation.
We study docstring generation for such routines with a small code model, and ask whether retrieving documented routines from the same code base helps.
We build a benchmark of 2,400 documented Fortran routines from six open-source scientific packages and generate docstrings for them with and without retrieval.
Retrieval with BM25 over the same package improves BLEU from 18.2 to 23.9, and in a pilot study, two domain experts prefer its docstrings in 64\% of 200 pairwise comparisons, with moderate agreement (Cohen's $\kappa = 0.41$).
Retrieval across packages helps much less.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Fortran is still widely used in scientific computing: climate models, solvers for partial differential equations and quantum chemistry packages depend on hundreds of thousands of lines of it.
New maintainers of such code often have to read a routine line by line to learn what its arguments mean, because the original authors have left.
Code models can write docstrings for popular languages, where training data is plentiful \citep{husain2019codesearchnet}, but they see little Fortran, and almost none of the conventions of a given package.

Retrieval-augmented generation \citep{lewis2020retrieval} offers a cheap fix: before writing a docstring, show the model documented routines that resemble the one at hand.
In this short paper we ask where those routines should come from.
We compare retrieval from the same package with retrieval from other packages, and find that the same package is far more useful.

\section{Method}
\label{sec:method}

Given an undocumented routine $x$, we retrieve the $k$ most similar documented routines $\mathcal{R}_k(x)$ with BM25 \citep{robertson2009probabilistic}, using identifiers and comments as the query and the standard parameters $k_1 = 1.2$ and $b = 0.75$.
The model then generates the docstring
\begin{equation}
\hat{y} = \argmax_{y} \; p_\theta\bigl(y \mid x, \mathcal{R}_k(x)\bigr),
\label{eq:rag}
\end{equation}
where the retrieved routines and their docstrings are prepended to the prompt; we use $k = 3$. % R1-03 Defined k here.
We decode greedily and cut the docstring at the first blank line.

\section{Experiments}
\label{sec:experiments}

Our benchmark holds 2,400 routines with docstrings written by their original authors, taken from six packages for climate, fluid dynamics and chemistry (between 180 and 610 routines each). % R1-04 Package sizes are here; the pair counts are in Table 1.
We hide each docstring, generate a new one, and compare it with the original using BLEU \citep{papineni2002bleu}.
Two domain experts also compared 200 pairs of docstrings, one with and one without retrieval, without knowing which was which.

Table~\ref{tab:results} shows the results.
Retrieval from the same package gains 5.7 BLEU points, while retrieval from other packages gains only 1.4.
The retrieved routines often share argument names and units with the routine at hand, and the model copies these conventions into its docstrings.

% R1-05 Ran the renaming test you suggested.
To test whether these conventions explain the gain, we renamed every identifier in one package to a neutral name (\texttt{v1}, \texttt{v2}, \ldots) and repeated the experiment on it.
The gain from same-package retrieval dropped from 5.7 to 2.1 BLEU points, while the gain from other packages did not change.

\section{Conclusion}
\label{sec:conclusion}

Retrieving documented routines from the same package is a simple way to help a small code model document legacy Fortran.
The gap between same-package and cross-package retrieval, together with our renaming test, suggests that local naming conventions matter most.
